# Дневник сборки TDlend

Проект выполняется с помощью ИИ-ассистента. Проверки браузерных сценариев выполняются управляемым браузером; в отчётах не приписываются студенту как лично выполненные.

## Исходная ситуация
Исходников сервиса записи у владельца нет. В предыдущей домашней работе по backend по ошибке была указана ссылка на PR другого проекта. Создан новый отдельный проект, существующие репозитории не изменялись.

## Ключевые задачи ассистенту
1. «Создать сервис записи с нуля: постоянная база SQLite, API, регистрация и вход, список услуг, запись и собственный кабинет. Не использовать фиктивные данные в браузере».
2. «Проверять поведение по циклу: падающий тест → реализация → успешный тест. На сервере проверять права, пересечение интервалов и длительность услуги».
3. «Подготовить админ-панель: отмена и перенос, услуги и мастера, блокировки; уведомлять клиента об изменениях».
4. «Для отчёта реально изменить название услуги в базе, обновить браузер, проверить ошибку входа и сравнить кабинеты двух разных клиентов».

## Принятые решения
- Новый репозиторий `inftverezovsky/skypro-tdlend`; предыдущие проекты не перезаписывать.
- Нативный Node.js 26 и SQLite без цепочки сторонних runtime-пакетов.
- Один адрес для API и интерфейса, cookie-сессия HttpOnly, никаких токенов в localStorage.
- Каталог услуг и мастеров заполняется из API. Начальное содержимое базы вымышленное и явно учебное.
- Дизайн: каталог и пошаговая форма записи, тёплый нейтральный фон и терракотовый акцент.
- Приватные материалы курса и локальные пароли не входят в публикуемый проект.

## Найденная проблема среды
Подключение к обычному Chrome не работало: основной профиль был заблокирован запущенным браузером. Причина установлена по ошибке инструмента: копирование профиля невозможно при открытом Chrome. Вместо закрытия пользовательских окон создан отдельный чистый профиль Chrome с локальным CDP и выполнено подключение Playwright. Повторная проверка: открывается личный кабинет Skypro после самостоятельного входа владельца, страницы и тесты доступны для чтения и действий.

## Фактическая приёмка

- `npm test`: 33 теста, 33 PASS, 0 FAIL. Проверены HTTP API, SQLite, авторизация, права, расписание, конфликты, уведомления, запуск CLI и сохранение данных после перезапуска.
- Сервис реально запущен на `http://127.0.0.1:3187`; GET /api/services вернул HTTP200 и три услуги из SQLite.
- Браузерная приёмка: 9 проверок PASS. Метка «Кедрозавр Даниила» появилась вместо «Стрижка», после проверки исходное название восстановлено. Цена 1800 и длительность60 не изменились.
- Неверный пароль: видимая строка «Неверный email или пароль» совпала с JSON-ошибкой API401.
- Кабинеты: у демонстрационного клиента была собственная запись; новый «Мирон Кедровый» увидел пустой кабинет, чужих записей не было.
- Клиент напрямую открыл /admin: HTTP403, «Доступ только для администратора».
- Конфликт: два независимых браузерных контекста заранее выбрали 2026-11-12,10:00, мастер Мария Волкова. Первый получил201 и запись№2. Второй —409 и «Это время уже занято или недоступно»; 10:00 исчезло из доступных кнопок.
- Администратор отменил запись№2. У клиента запись осталась с пометкой «Отменена»; счётчик0→1, уведомление «Запись «Стрижка» на 2026-11-12 10:00 отменена администратором.».
- Перенос записи№1 на14:00 выполнен через форму администратора: id сохранён, новое время появилось в кабинете владельца.
- На viewport390px ширина документа375px, горизонтального переполнения нет. Скриншот реально просмотрен. Исключений JavaScript не зарегистрировано;401/403/409 в негативных сценариях ожидаемы.

## Проблема проверочного сценария и повторная проверка

Первый запуск browser-runner остановился при поиске select по точной доступной подписи «Мастер». Реальная страница уже показывала форму и список мастеров; ошибка была в слишком строгом локаторе теста, не в загрузке сервиса. По сохранённому состоянию браузера установлен правильный select внутри формы записи. Исправлен только локатор runner, код приложения не менялся. Повторная проверка прошла все9сценариев. Первоначальные неудачные receipts сохранены отдельно, а не переименованы в PASS.

## Исправления после независимой проверки

Обнаружены три ошибки пограничных сценариев: при успешном сохранении записи и неудачном чтении URL оставался на форме записи; нетронутый административный select мог восстанавливать старый статус поверх свежего; после ошибки загрузки собственного кабинета в состоянии оставался общий административный список.

Для каждой ошибки сначала получен падающий регрессионный тест, затем исправление и успешный повтор. Итоговый `npm test` после исправлений: **38 PASS, 0 FAIL, 0 SKIP**. Исходные 33 PASS выше относятся к предшествующей версии; они не выдаются за проверку последующих изменений.

Дополнительно в реальном браузере выполнены три проверки с явно внедрённым разовым HTTP503 на границе чтения (это контролируемая имитация сбоя, не наблюдавшаяся авария сервера):
- POST записи реально сохранил запись, первый GET был искусственно отклонён, URL остался `#cabinet`; «Обновить записи» сделал второй GET без второго POST. Счётчики: POST1, GET2.
- При переходе из админки в кабинет и искусственной ошибке собственного GET не показано ни одной чужой карточки или кнопки отмены.
- После внешнего изменения статуса на cancelled нетронутая форма при возврате в админку показала актуальное cancelled, а не старое confirmed.

Таким образом, причина установлена по выполнению реальных контроллеров и браузерных действий, исправления повторно проверены; описание дефектов не основано лишь на предположениях модели.

## Сдача и непроверенные границы

Полные текстовые отчёты по frontend и админ-панели отправлены в Skypro. После новой загрузки страницы наличие каждого полного текста подтверждено; статус обоих — «Задание на проверке». Это не оценка наставника.

На момент первоначальной приёмки локальный Docker Engine был недоступен; публичный деплой, HTTPS и внешний OAuth тогда не проверялись. Последующее размещение описано ниже отдельно.

## 11 ноября 2026 — backend и публичное размещение

- Независимая проверка нашла две ошибки доступности: перенос использовал новую длительность услуги вместо сохранённой длительности записи, а повторная активация отменённой записи не проверяла занятость. Обе исправлены через RED → GREEN; независимый delta-review принял исправления. Перед публикацией полный локальный `npm test` дал **58 PASS / 0 FAIL**.
- Код опубликован в GitHub. На Linux VPS выделены собственные каталог `/opt/skypro-tdlend`, контейнер `skypro-tdlend` и адрес `https://tdlend.82.147.67.245.sslip.io/`. Чужие приложения, контейнеры и nginx-файлы проверены по исходному реестру и сохранены; удалений не выполнялось.
- Первый архив Git, созданный в Windows, не прошёл проверку SHA исходника: Git применил преобразование LF → CRLF. Проверка остановилась до Docker build и запуска. Новый архив создан с `git -c core.autocrlf=false archive`; все 35 файлов сравнены с соответствующими Git blobs. Первый архив и его каталог сохранены, а не заменены.
- Образ действительно собран и запущен на Linux/amd64 от пользователя `node`. SQLite находится в отдельном постоянном bind mount, а приложение слушает только loopback за nginx. Получен сертификат Let's Encrypt; HTTP возвращает перенаправление 301 на HTTPS, страница и API по HTTPS возвращают 200.
- На публичном адресе выполнены 9 браузерных проверок: регистрация с Secure/HttpOnly/SameSite cookie, разные кабинеты, создание записи, конфликт 409, отмена и уведомление, запрет `/admin` с 403, сохранение входа после обновления, мобильная вёрстка, отсутствие исключений JavaScript. Использованы только вымышленные аккаунты. Запись №3: «Стрижка», Мария Волкова, 2026-11-12 10:00; после отмены история сохранилась.
- Первая публичная проверка уведомления нажала кнопку до завершения начальной загрузки и получила таймаут. После ожидания фактического завершения чтения данных весь сценарий повторён успешно. Это уточнение проверочного сценария, не исправление приложения; первая неудача сохранена отдельно.
- Создана согласованная SQLite backup-копия: `integrity_check = ok`. Все три существовавшие на тот момент записи по всем полям строк совпали до и после контролируемого перезапуска только нового контейнера. Копия базы также сохранена на ПК; она не публикуется.
- Первый GitHub Actions прогон: Linux-container PASS, node-tests FAIL (55/58). Причина — тесты предполагали наличие TMPDIR или TEMP, отсутствующих на Linux runner. Исправлены только два тестовых файла добавлением `node:os.tmpdir()` как последнего fallback, без ослабления бизнес-проверок. Повторный реальный CI для `f6b1ff5e8f12cb9edd0533ad2bb07bb30ffdb57a`: оба job SUCCESS. Linux-container проверил HTTP, сессию и сохранение SQLite после restart собственного одноразового CI-контейнера.
- Видео: реальный локальный скринкаст 4:45 с восемью обязательными действиями и русскими титрами; весь MP4 декодирован ffmpeg без ошибок. Он относится к **базовому уровню**, не выдаётся за запись публичного сервера.

## Оставшиеся границы

Вход через Яндекс не реализован и не проверен; Coolify, Vercel для этого сервиса и автодеплой на VPS не настраивались. Домен не покупался: используется бесплатное DNS-имя sslip.io. Не выдаём это за выполнение расширенного уровня или полного урока OAuth. После защиты сервер и данные не удаляются автоматически: владелец прямо запретил удаление. Остановка собственного контейнера и последующая судьба проекта требуют отдельного решения владельца.
