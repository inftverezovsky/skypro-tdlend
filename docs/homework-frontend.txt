Отчёт о подключении экранов
Проект: TDlend — учебный сервис записи в студию ухода.
Проверки выполнены с помощью ИИ-ассистента в реальном Chrome на запущенном сервисе; ниже приведены фактические результаты, а не предполагаемое поведение.

1. Три экрана
• «Услуги» — public/index.html, представление services в public/ui.mjs, точка входа public/app.js — GET /api/services. Показывает название, описание, длительность и цену услуг из базы, кнопку перехода к записи.
• «Вход» — public/index.html, представление login в public/ui.mjs — POST /api/auth/login. Показывает форму email/пароля и дословную ошибку сервера; после успешного входа открывает кабинет. Сессия передаётся HttpOnly-cookie, токен в localStorage не сохраняется.
• «Личный кабинет» — public/index.html, представление cabinet в public/ui.mjs — GET /api/bookings. Показывает только записи вошедшего клиента: дату, время, услугу, мастера, сохранённую цену, статус и доступное действие отмены.
Это разные состояния одного приложения, а не три независимых HTML-файла.

2. Проверка: откуда экран берёт услуги
Слово-метка: «Кедрозавр Даниила».
Через административный API изменено в базе название услуги «Стрижка», id 1. Страницы, стили и код при этой проверке не менялись.
После обновления страницы первая строка каталога называлась «Кедрозавр Даниила». Под ней остались «Форма и укладка», «60 мин» и цена «1 800 ₽».
Вывод: название загружается из базы через API, а не вписано в HTML. Исходное название «Стрижка» затем возвращено тем же способом; повторное чтение API подтвердило восстановление.

3. Проверка: неверный пароль
В форму введён email демонстрационного клиента client@tdlend.local и заведомо неправильный тестовый пароль; нажата кнопка «Войти».
Дословный текст на форме: «Неверный email или пароль».
Источник установлен не по внешнему виду: запрос POST /api/auth/login вернул HTTP 401 и JSON с тем же полем error. Содержимое видимого сообщения сопоставлено с ответом сервера — строки совпали. Затем вход с правильными локальными учётными данными прошёл успешно.

4. Проверка: кабинеты двух клиентов
Первый клиент — «Демо-клиент». На момент сравнения в кабинете была одна запись: 2026-11-12, 10:00, услуга «Стрижка», мастер Анна Смирнова, цена 1 800 ₽, статус «Подтверждена».
В отдельной независимой браузерной сессии зарегистрирован второй клиент «Мирон Кедровый», email miron.qa.28b76545@example.test. После регистрации в его кабинете показаны «Пока нет записей», «Самое время запланировать небольшой перерыв для себя.» и кнопка «Выбрать услугу ↗». Записи первого клиента не появились.
Вывод: кабинеты отличаются, сервер выдаёт записи текущего владельца. Использованы вымышленные учебные данные.

5. Что могло бы сломаться
Все три проверки прошли; следующий разбор гипотетический, это не описание найденного дефекта.
Что было бы видно: после изменения услуги в базе в каталоге осталось бы старое название.
Возможная причина: экран использует строку из разметки либо не перечитывает API; версию нужно проверить по реальному ответу GET /api/services и содержимому страницы, а не принимать на веру.
Исправление: подключить вывод названия к ответу API, не меняя оформление карточки; затем повторить подмену, обновление и восстановление. В проведённой проверке подмена и восстановление уже подтверждены браузером и API.
